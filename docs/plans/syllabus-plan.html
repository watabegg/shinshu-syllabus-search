目的と背景

本計画は、信州大学におけるキャンパス情報システムの停止に伴う暫定措置として、学内構成員（学生および教職員）が2026年度の講義情報を迅速かつ横断的に検索できるようにするための検索基盤に関する調査結果と実装計画をまとめたものである。対象データは、大学により一般公開されている2026年度分のシラバス情報に限定する。

本計画における対象範囲（In scope）および対象外（Out of scope）の境界は以下の通りである。

  • 対象範囲（In scope）:
  • 大学の公開ポータルHTMLからの講義一覧および階層構造の取り込み
  • 各シラバスPDFの取得とテキスト情報の抽出
  • 講義名、担当教員名、登録コード、講義本文を対象とした横断検索機能の提供
  • 検索結果一覧および講義詳細画面における講義情報・原本出典URLの表示
  • Cloudflare Workers（workers.dev ドメイン）へのシステム配備
  • 対象外（Out of scope）:
  • 履修登録、成績照会、出席管理などの学務業務機能
  • 利用者のログイン認証およびセッション管理
  • お気に入り登録や講義のブックマーク保存機能
  • 生成AIを用いたシラバスの自動要約やベクトル検索（意味検索）
  • 過年度シラバス情報の推測やデータの補完
  • 原本PDFの独自再配信（大学公式の公開URLへの外部リンク表示にとどめる）
  • 外部サーバに対する高頻度な自動巡回クローラの常駐運用

要件定義において、本システムは学内全員の利用を想定した「認証不要の一般公開検索サイト」として運用することが確定している。検討初期に挙がっていた学内Googleアカウント限定の認証方針は撤回されており、認証テーブルの設計、認証ルートの実装、Google OAuth連携設定、およびCloudflare Accessの設定はすべて不要である。また、独自ドメインの新規購入は行わず、将来的にCloudflareの指定アカウント配下の workers.dev ドメインへデプロイする。

なお、現行の公開ポータルに掲載されているシラバスは認証なしで取得可能な状態にあるが、これは技術的に取得できるという事実を示すものに過ぎず、本システムでの二次利用や転載の条件を保証するものではない。転載条件に関する具体的な調査は未完了であり、本計画において法的判断は下さない。画面上には取得日時と原本リンクを必ず明示し、利用者に大学公式の原本確認を促す運用とする。

Problem と Solution

現行のシラバス閲覧環境における課題と、本システムによる解決方針を以下に整理する。

  • 学部・部局ごとの分断（Problem）: 現行の公開形態では21の学部・研究科ごとにページが分かれており、共通教育科目や他学部の関連講義を探すには、利用者が各部局のページを個別に開いて往復する必要がある。
  • 解決方針（Solution）: 全学の全講義データを単一のデータベースへ統合し、部局の枠組みを越えて一括検索できる全学横断インデックスを提供する。
  • 検索対象の限定（Problem）: 現行の検索スクリプトは画面上に表示された講義名と登録コードの文字列しか照合できず、担当教員名や、講義概要・達成目標などのシラバス本文を対象とした検索が一切行えない。
  • 解決方針（Solution）: 各シラバスPDFからテキスト情報を事前に抽出し、タイトル、担当教員名、登録コード、講義本文を網羅した全文検索インデックスを構築する。
  • 同名講義の識別困難性（Problem）: 基礎的な科目等では同一の講義名を持つ授業が多数開講されており、担当教員、時間割、所属部局が異なるにもかかわらず、講義名だけでまとめられると受講対象のコマを判別できない。
  • 解決方針（Solution）: 同名講義を安易に同一レコードへ集約せず、登録コード、担当教員名、開講スロット（学期・曜日・時限）、掲載区分を検索結果カードおよび詳細画面に明記し、それぞれ独立した講義として識別できるように表示する。

設計判断と代替案

1. システムアーキテクチャの選定

本システムでは、単一のCloudflare Workers上にStatic Assets、Hono、@hono/inertia、React、およびshadcn UIを組み合わせた構成を採用する。

  • 採用構成:
  • フロントエンドとバックエンドの結合: HonoとReactを @hono/inertia で接続し、単一のWorkerからSPA（Single Page Application）の軽快な操作感とサーバサイドのルーティング・データ供給を両立させる。
  • データベース接続: Cloudflare D1を採用し、SQLの直接バインディングを実行する。初期開発段階ではORM（Object-Relational Mapping）を導入せず、直接SQLを発行して構成の簡潔さと実行効率を担保する。
  • PDF抽出パイプライン: サーバレス環境上でのリアルタイム抽出は行わず、ローカル環境のPythonとPopplerを用いたバッチ抽出スクリプトを手動CLIで運用する。
  • 不採用とした代替案:
  • Cloudflare R2: 原本PDFは大学の外部公開URLを直接参照し、抽出テキスト原本はローカルに保持するため初期構成では不要である。
  • Cloudflare Queues / Workflows: 高頻度な自動クロールや非同期分散処理はスコープ外であるため初期構成から除外する。
  • React Router / 別個のREST API / Hono RPC: Inertiaのpropsを通じて型安全にデータを受け渡すため、クライアントサイドルーティングライブラリやRESTエンドポイントの個別定義は不要である。Hono RPCは、将来的にサードパーティ向け外部APIを提供する要件が生じた段階で初めて検討する。
  • 技術的根拠:
  • 設計動機: Zenn記事 Hono + Inertia.js + ReactでCloudflare Workers上にフルスタックSPAを構築する動機と設計 の構成方針を踏襲する。
  • 公式仕様: Hono公式リポジトリ @hono/middleware/packages/inertia に示されているReact、Vite、Cloudflare Workersの公式統合パターンに準拠する。

2. データベース選定と日本語全文検索エンジン

全学の対象シラバスは約6,461件（PDF数）であり、データ規模としては数千レコード程度である。この規模であれば、分散RDBMSや外部全文検索サービスを導入せずともCloudflare D1で十分に要件を満たせる見込みがある。

  • D1の選定根拠:
  • Cloudflare D1では標準でSQLiteのFTS5拡張およびtrigramトークナイザが利用可能である（参考: Cloudflare D1 SQL Statements および Cloudflare D1 Best Practices: Use indexes）。
  • PostgreSQL等の外部マネージドデータベースは、ネットワークホップの発生や構成の複雑化、コスト増加を招くため初期段階では採用しない。D1の実測で検索性能や表現力に不足が確認された場合に限り再検討を行う。なお、D1にはPDFのバイナリデータは格納せず、抽出・正規化されたテキスト情報のみを保持する。
  • 日本語テキストの正規化仕様:
  • 検索対象となるタイトル（title）、担当教員（teacher）、登録コード（code）、本文（body）の各列について、検索専用のテキストカラムを用意する。
  • 検索用カラムにはUnicode NFKC正規化、小文字化（lowercase）、および連続空白の単一化を施す。
  • 画面表示には正規化前の原文データを保持し、データ投入時と検索クエリ発行時で全く同一の正規化ロジックを適用する。
  • trigramの制約に伴うクエリ分岐:
  • ローカルのSQLite環境での検証により、trigramインデックスでは2文字以下のトークン（例: 「情報」「数値」）に対してMATCH演算子による検索が行えない（ヒットしない）仕様が確認されている。
  • したがって、検索クエリの処理ではトークン長に応じた分岐処理を実装する。
    • 3文字以上のトークン: ダブルクォーテーションで囲んだ安全なFTS5 MATCHクエリ（quoted MATCH）を発行する。
    • 1〜2文字のトークン: SQLiteの組み込み関数 instr を用いた部分一致走査へ分岐させる。B-Tree絞り込み後の instr 走査の応答性能については、D1への全量データ投入後に実測して検証する。
    • 混在時の処理: 3文字以上の語と1〜2文字の語が同時に指定された場合は、まず3文字以上の語でFTS5により候補レコードを絞り込み、その結果集合に対して短語の instr 条件を適用する。
  • LIKE 演算子は、D1において検索パターンが50バイトを超えた場合にエラーとなる制限が存在するため採用せず、部分一致には instr を用いる。
  • 入力バリデーションと検索パラメータ:
  • 検索キーワードは最大100文字、最大5トークンまでとし、各トークンの長さは最長40文字に制限する。
  • 複数トークンは空白区切りによるAND検索として扱い、検索文字列が空の場合は全件一覧を返す。
  • 部局（department）、年度（year）、学期（term）などの絞り込み条件は定義済み列挙型（enum）で検証し、通常インデックス（B-Tree）を適用する。
  • ページネーションは整数 page >= 1、1ページあたり固定20件の表示とする。
  • FTS5の特殊記号はエスケープした上でSQLバインドパラメータとして安全に引き渡す。
  • ランキング順位は、タイトルの一致（完全一致・前方一致） → 登録コードの一致 → 本文スコアの順に評価し、最終的に course.id でソートして表示順の決定性を担保する。ランキングの微調整は実装ステップのfixtureテストで確認し、短語検索性能は全量データ投入後に実測する。全文bigramインデックスの追加は実測で必要と判断された場合のみ行う。

3. キャッシュ戦略

一般公開サイトの特性を活かしたキャッシュ設計を行うが、開発初期における複雑性の混入を防ぐため段階的なアプローチを採る。

  • MVP（初期リリース）の方針:
  • 動的HTMLおよびInertia用JSONレスポンスには Cache-Control: no-store を設定し、WorkerのデフォルトエントリポイントにおけるWorkers Cacheも無効化する。
  • キャッシュ対象はコンテンツハッシュが付与された静的アセット（JS/CSS）のみとし、まずはD1に対する素のクエリ性能と処理速度を計測する。
  • 将来的な最適化設計:
  • D1への負荷軽減が必要となった場合は、外側のデフォルトエントリポイントはuncachedのままとし、内部の検索データ専用エントリポイント（search data entrypoint）に対してWorkers Cache（TTL 5分）を導入する。
  • キャッシュキーは「正規化クエリ + フィルタ条件 + ページ番号 + データリビジョン番号」で構成し、HTMLレスポンスとInertiaのJSONレスポンス（X-Inertia ヘッダ要求）が同一キーで混ざらないよう分離する。
  • 将来的に学内認証が再導入された場合でも、外側のエントリポイントで毎リクエスト認証認可を検証できる構造を担保する。
  • 技術的根拠:
  • 旧来のCache APIと新しいWorkers Cacheを同一視しないこと。新Workers Cacheは workers.dev 環境でも利用可能であり、Worker単位でキャッシュが管理され、キャッシュヒット時はハンドラの実行自体を省略して高速に応答する（参考: Cloudflare Workers Cache Documentation および Workers Cache Examples）。内部エントリポイントは外部URLで直接ルーティングされないため安全性が高い。初期段階ではキャッシュの複雑性を持ち込まず、性能測定結果を踏まえて適用を判断する。

4. データ同定規則と重複排除ポリシー

  • 同名講義の独立性保持: 科目名が同一であっても、安易に1つの講義レコードへ統合してはならない。教員や開講区分、時間割が異なる講義はそれぞれ独立した講義として扱う。
  • 原本PDFの重複排除: 公開ポータル内の複数箇所からリンクされている同一PDFは、元URL（source canonical URL）をキーとしてダウンロードおよびテキスト抽出の重複を排除する。
  • 自然キーと主キーの設計: 講義エンティティの自然キーは暫定的に 開講年度(year) + 掲載区分(department) + 登録コード(code) の組み合わせとする。データベース上の主キーにはこれとは独立した一意のID文字列（UUID等）を割り当てる。
  • 開講スロット（時間割）の複数行保持: 1つのシラバスPDF内に複数の開講曜日や時限が記載されている場合、講義レコード自体を別講義へ分割してはならない。講義テーブル（course）に対して開講スロットテーブル（course_slots）を1対多で関連付け、学期（term）、曜日（day）、時限（period）の組み合わせを行単位で保持する。これにより、未定、集中講義、複数時限開講を単一の時限へ潰すことなく正確に記録する。
  • データ競合（Conflict）の検知と運用調整: 同一の自然キーでありながら、異なるPDF URL、担当教員、または時間割の食い違いが検出された場合は、自動的な上書き統合を行わず、コンフリクトとして警告を記録して処理を保留する。この競合は運用者がバリアントキー（variant key）を手動で指定して解除する運用とする。ユーザーの判断による運用調整を許容し、もし「同一の登録コードでありながら全く別の講義である」という反例が判明した場合は、自然キーの設計自体を見直す。
  • データ整合性の検証: 登録コードの照合はPDF本文とポータルHTMLの記述双方を突き合わせて行い、HTML側の時間割表記とPDF本文の記述に差分がある場合は警告ログを出力する。なお、PDFに複数時限が記載されていることのみを理由として別講義へ分割してはならない。

API仕様の変更

提供するAPIエンドポイントはすべて新規設計であり、既存システムとの後方互換性を考慮する必要はない。すべてのエンドポイントは認証不要で利用可能であり、HTTP GETメソッドのみで構成され副作用を持たない。

1. 講義一覧検索: GET /

講義の検索、絞り込み、およびページ送りを担うエンドポイントである。Inertia.jsによる画面描画とJSONデータ取得の双方で共通のデータ構造を返却する。

  • クエリパラメータ:
  • q（文字列、任意、初期値: 空文字列）: 全文検索キーワード。画面表示時はHTMLエスケープを徹底する。
  • year（整数、任意、初期値: 2026）: 開講年度。存在しない年度が指定された場合はHTTP 400を返す。
  • department（文字列、任意）: 学部・研究科の識別子（列挙値）。
  • term（文字列、任意）: 開講学期（列挙値）。
  • page（整数、任意、初期値: 1）: ページ番号。page > 1000 の場合は極端なオフセット指定による高負荷を抑止するため固定上限としてHTTP 400を返す。
  • 返却プロパティ（Props）:
  • items: 講義概要オブジェクトの配列。各要素は { id, title, code, teacherText, department, slots } で構成される（teacherText は未設定時 null）。
  • page: 現在のページ番号。
  • hasNext: 次ページの有無を表す真偽値。総件数（count）の全件走査は初回リクエストの高速化のため行わず、表示件数20件に対して1件余分に取得（20 + 1行取得）することで判定する。
  • filters: 現在適用されている絞り込み条件（q, year, department, term）。
  • availableFilters: 絞り込みに利用可能な選択肢一覧（年度、学部、学期）。
  • importedAt: データが最後に同期された日時。
  • coverage: システム全体のデータ取り込み状況 { discovered, ready, failed, conflict }。
  • ステータスコードと挙動:
  • 200 OK: 検索成功。該当結果が0件の場合も空配列を含めて 200 OK を返す。
  • 400 Bad Request: 不正なクエリ形式、範囲外のページ番号（page > 1000）、存在しない年度の指定。
  • 429 Too Many Requests: レート制限超過時。
  • 503 Service Unavailable: データベース利用不可時。

2. 講義詳細取得: GET /courses/:id

指定された単一講義の全文、メタデータ、および解析状況を取得するエンドポイントである。

  • パスパラメータ:
  • id（文字列、必須）: 講義の一意な識別子。
  • 返却プロパティ（Props）:
  • course: 講義の基本情報（タイトル、科目コード、教員名、単位数、開講学期など）。
  • sections: 抽出された本文の各セクション（構造化データ）。
  • pages: ページごとの原文テキストおよび検索用正規化テキスト。
  • sourceUrl: 元のシラバスPDFのURL。外部への不正な誘導やSSRFを防ぐため、許可されたホスト名および /syllabus 配下のパスのみを保持・返却する。
  • sourceSha256: 取り込み時のPDFファイルのSHA-256ハッシュ値。
  • fetchedAt: 該当PDFを最後に正常取得した日時。
  • parseWarnings: テキスト解析時に発生した警告内容の配列。
  • ステータスコード:
  • 200 OK: 取得成功。
  • 404 Not Found: 存在しないID、または未公開状態のIDが指定された場合。

3. ヘルスチェック: GET /healthz

システムの稼働状態を監視するための軽量エンドポイントである。内部状態を詳細に開示せず、サービス提供が可能か否かの最小限の情報のみを返す。

  • ステータスコード:
  • 200 OK: 正常稼働中（WebサーバーおよびD1データベースへの疎通確認が成功）。
  • 503 Service Unavailable: D1接続不能などの致命的障害発生時。

4. 共通プロトコル規約

  • コンテンツネゴシエーション: Accept: text/html および X-Inertia: true ヘッダーを伴う要求はInertia.jsの公式アダプターによって適切に処理される。Accept: application/json の要求に対しても、公開用の同一データ構造を返却する。
  • 原本URLの制限: 講義情報に含まれる原本シラバスのリンク（href）は、許可されたホスト名かつ /syllabus から始まるパスのみに制限し、外部サイトへの不正リダイレクトを防止する。

2. 0002_search.sql（全文検索インデックス）

全文検索機能にはSQLiteのFTS5拡張仮想テーブルを利用し、3文字以上のトークン向けにトークナイザーとして trigram を採用する。なお、1〜2文字の短語検索には instr 関数による部分一致走査へ分岐させる。

-- FTS5スタンドアロン仮想テーブルの作成
CREATE VIRTUAL TABLE course_search USING fts5(
    title,
    teacher,
    code,
    body,
    tokenize = 'trigram'
);
  • FTSとベーステーブルの連携方式: FTS5テーブルと基本テーブルの紐付けには中間テーブル（course_search_rows 等）を新設せず、courses テーブル上に保持する search_rowid INTEGER UNIQUE NOT NULL を直接利用して course_search の暗黙的な rowid と1対1で対応付ける。
  • トリガーの不採用とバッチ更新: SQLiteの外部コンテンツトリガーは使用せず、講義データを取り込む際に courses, course_pages, course_slots, course_search を同一のD1バッチ処理内で同期的に挿入・更新・削除する。これにより、トリガー起因の予期せぬ制約違反を回避し、D1のトランザクション境界を明示的に制御する。
  • 検索対象テキスト（body）の構成: course_search の body カラムには、正規化された全ページの search_text を結合した文字列を格納する。書式や改行を含む生のテキストは course_pages.raw_text に保持する。シラバスPDF内の各見出しセクションは courses.raw_metadata_json 内に任意の派生データとして保存し、初期段階ではPDFセクション構造に対する厳密なスキーマ固定は行わない。

D1制約と更新トランザクション設計

Cloudflare D1の制約に対応するため、以下の設計基準を適用する。

  1. バインド変数とリクエストサイズ制限への対処: D1には「各SQL文あたり100個のバインド変数上限（bound params per query）」「1行あたり最大2MB」「1クエリSQLサイズ最大100KB」という制限が存在する。講義データ（courses）、ページ（course_pages）、時間割枠（course_slots）、および検索インデックス（course_search）の登録は、各文の上限に配慮しつつ講義単位（1件ごと）にバッチとしてアトミックにコミットする。ページ分割後であっても、FTS検索用インデックス（course_search）に集約結合する本文全体のサイズが1行2MB上限を超過しないか検証を行う。極端に巨大なPDF（暫定で10MiB超のもの）はインポート対象から隔離し、個別エラーとして記録する。
  2. 講義単位のアトミック性と過去データの保持: データベース全体を一括更新する巨大トランザクションは実行できないため、取り込み処理は講義単位で実施する。更新フェーズ中にクローラーが特定PDFの再取得に失敗した場合でも、既存の正常な講義レコードを削除せず、source_documents.last_attempt_status = 'failed' として前回の正常データを保持（stale状態としてフラグ付け）する。UI上には最後に成功した fetchedAt と最新の試行ステータスを並行して表示する。
  3. ステージング検証と本番バインディング切り替え: 初回の全量インポートは新規作成したステージング用D1データベースに対して実行し、検証完了後にWorkersのD1バインディングを本番環境へ切り替える。この方式により、取り込み処理の途中段階で不完全なデータが公開されるリスクを回避する。また、旧D1データベースのバインディング定義を保持しておくことで、障害発生時の迅速なロールバックを可能にする。初回取り込みで partial（一部失敗）となった場合は本番バインディングへの差し替えを停止する。

通信エラーと再試行制御方針

  • HTTP 404（Not Found）: 原本URLの消失と判断し、エラーログに専用分類で記録する。短時間の再試行（リトライフラッド）は行わず、次回インポート周期まで再アクセスを抑止する。
  • HTTP 429（Too Many Requests）および 5xx（Server Error）: 相手先サーバーの過負荷を考慮し、指数バックオフ（Exponential Backoff: 初回1秒、2回目2秒、3回目4秒）を伴う最大3回までの再試行を実施する。3回すべて失敗した場合は failed として記録する。
  • タイムアウト: 30秒を上限とし、タイムアウト発生時は直ちに切断してログを記録し、次回再試行対象とする。
  • インポート全体の判定:
  • completed: 発見された全URLの処理が完了し、failed_count = 0 かつ conflict_count = 0 の場合。
  • partial: 処理は完走したが、一部の文書で failed または conflict が残存している場合。
  • failed: インデックスHTMLの一覧列挙に失敗するなど、処理自体が中断した場合。

セキュリティ・プライバシー・可観測性

本システムは学内利用者を主対象としつつ認証を設けない一般公開の検索サービスとして運用する。誰でもアクセスできる公開構成をとるため、外部データを取り込むパイプラインと検索画面の双方で安全性を確保する。

外部の HTML や PDF から抽出した本文、および SVG などの描画要素には、意図しない制御文字やスクリプトが混入する懸念がある。そのため、抽出したテキストは描画前にエスケープ処理を施し、React の dangerouslySetInnerHTML に直接渡す実装は禁止する。サーバーとフロントエンド間のデータ連携には Inertia.js 公式のシリアライザを使用し、安全なデータバインディングを維持する。

データ収集クローラーは、あらかじめ定めた固定ドメインおよび固定パスのみを巡回対象とする。外部へのリダイレクトが発生した場合にも遷移先のドメインとパスを再検証し、予期しないエンドポイントへの通信を遮断する。また、外部からの意図しないデータ書き込みを防ぐため、取り込み処理を行う Web API は外部公開せず、開発者が実行する管理用 CLI に限定する。

不特定多数のアクセスによる過負荷を防ぐため、検索エンドポイントにはレート制限を導入する。基準としては IP アドレスあたり毎分 60 リクエスト程度を目安とするが、固定仕様として決め打ちにせず、稼働後の負荷測定に基づいて調整する。特に学内 LAN などの共有 IP アドレスから多数の利用者が同時接続する状況を考慮し、正当な利用を阻害しない閾値と除外基準を設定する。

プライバシー保護の観点から、シラバス原本全文の保持に伴い本文中に記載された公開連絡先等はそのまま保持されるものの、PDFの作成者情報等の不要なメタデータ（文書プロパティ等）を別途収集することはせず、またログ等に個人連絡先を出力しないよう配慮する。

ログ管理においては、利用者のプライバシー保護と情報漏洩防止のため、検索クエリ（q）、教員の個別連絡先やメールアドレス、シラバスの原文テキスト、認証情報やトークン（credentials）は一切記録しない。可観測性の確保に必要なメトリクスとして、リクエスト処理時間（duration）、HTTP ステータスコード（status）、Cloudflare D1 の読み取り行数（rows_read）、取り込み件数カウンター（import counters）、外部データ取得時のエラー情報（source errors）のみを出力する。Cloudflare Worker の実行に必要なデプロイトークンは既存の環境変数を通じて設定されており、Git リポジトリ内には保存しない。

ロールアウト

安全なサービス公開とトラブル発生時の迅速な切り戻しを実現するため、段階的なデプロイ手順とデータベース管理方針を定める。

公開に向けた移行手順は、抽出成功を確認したサンプルデータ（21 件、うち目視確認済は1件1ページのみ）を用いた動作確認から開始し、公開前のサンプル人手照合およびステージング環境における全量データ（約 6,400 件）の取り込み検証を経て、一般公開へ進める。原本の PDF ファイルそのものは本サービス内で再配信やホスティングを行わず、信州大学の公式ページへの外部リンクのみを提供する。

本番データベースへの反映には、新規の Cloudflare D1 インスタンス（fresh D1）を作成してデータを投入・検証した上で、Worker の接続先を切り替える方式（本番スイッチ）を採用する。移行前の旧データベースインスタンスを保持しておくことで、重大な不整合や障害が発生した場合でも即座に以前の状態へ接続を戻せる構成とする。

公開後のデータ更新については、月次または新学期（春学期・秋学期）の開始時期に手動の更新コマンドを実行する運用を提案する（具体的な更新日程は大学の公開スケジュールを踏まえて確定する）。データ更新の遅延や一部科目の欠落が生じた場合に利用者が混乱しないよう、検索画面上に対象データの網羅率（coverage）と最終取得日時を表示する。

デプロイ先となる Cloudflare 環境の現状として、workers.dev のサブドメインが未登録であり、API アクセスに対して 404 エラーが返却される状態にある。本番デプロイに先立ち、適切なサブドメインの登録と設定を行う必要がある（権限やエラー状況に応じて再確認する）。なお、本システムでは利用者側からのデータ変更操作（リモートミューテーション）は一切提供しない。

リスクと対策

本システムのデータ構造および外部依存関係に起因する主なリスクと、それに対する具体的な対策は以下の通りである。

  1. PDF からのテキスト抽出精度と誤抽出 - 課題: pdftotext によるテキスト抽出自体は可能であるものの、表組みの境界判定の失敗、段落の折り返しや改行の乱れ、科目コードや担当教員名などのメタデータの誤抽出が発生する可能性がある。 - 対策: 抽出処理において信頼度（confidence）が低いと判定されたフィールドは値を無理に確定させず、NULL として扱う。その上で原本テキストと警告表示を併記し、人手で大学の原本情報と照合できるようにする。
  2. 講義総数の不確定性 - 課題: 事前調査で判明した 6,461 件という数値はユニークな PDF URL の総数であり、実際の開講講義数と一致するとは限らない。同一科目の複数スロットや休講情報が含まれている可能性がある。 - 対策: 検索画面上に注記を配置し、最新の時間割や開講状況については大学公式の原本情報を優先して確認するよう誘導する。
  3. 全 PDF における OCR 不要仮説の限界 - 課題: サンプル調査として検証した 21 件の PDF では OCR なしでテキスト抽出が可能であったが、全 6,461 件のすべての PDF において OCR 処理が不要であると断定することはできない（スキャン画像による PDF が混在している可能性がある）。 - 対策: 抽出に失敗した場合は低信頼度フィールドと同様に扱い、原本リンクと警告を併記して人手照合に委ねる。
  4. 大学側公開サーバーへの過負荷 - 課題: クローラーによる短時間の集中アクセスが、大学のサーバーに負荷をかける恐れがある。 - 対策: クローラーの接続頻度を制御し、リクエスト間に最低 1 秒以上の間隔（1 リクエスト/秒以下）を空けて順次取得を行う。
  5. D1 の短期的費用と制限超過 - 課題: 大量の全文検索インデックス作成や全件走査により、D1 の書き込み・読み取りクォータを短期間で消費し、費用や制限に抵触する懸念がある。 - 対策: 事前調査に基づく料金・クォータ制限（付録 A 参照）に沿って分割取り込みや適切なインデックス設計を行う。
  6. 大学側サイト停止時の影響 - 課題: 大学のシラバス公開サーバーがメンテナンスや障害で停止する可能性がある。 - 対策: 一度取り込んだデータは Cloudflare D1 上に蓄積されているため、元サイトが停止している間も本サービス内での検索・閲覧は継続して稼働する（原本リンクへのアクセスのみが一時的に不能となる）。

3. Cloudflare D1 および Workers の制限と料金体系

Cloudflare D1 は FTS5 trigram に対応しており、システム設計に関わる主要な制約と料金体系は以下の通りである。 - 制約・上限仕様: - LIKE パターンの上限は 50 バイト。 - 1 行あたりのサイズ上限は 2 MB。 - バインドパラメータの上限は 100 個。 - 1 クエリあたりの SQL サイズ上限は 100 KB。 - データベース容量は無料枠で 1 DB あたり 500 MB（アカウント全体で 5 GB）、有料プラン（Paid）で 1 DB あたり 10 GB。 - 詳細は Cloudflare D1 Limits を参照。 - D1 料金体系: - 無料枠: 1 日あたり 500 万行の読み取り（5M rows read/day）、1 日あたり 10 万行の書き込み（100k rows write/day）。 - 有料枠: 月間 250 億行の読み取り（超過時は 100 万行あたり $0.001）、月間 5,000 万行の書き込み（超過時は 100 万行あたり $1.00）、5 GB のストレージを含む（超過時は 1 GB あたり月額 $0.75）。詳細は Cloudflare D1 Pricing を参照。 - Workers 料金体系: - 無料枠: 1 日あたり 10 万リクエスト（100k requests/day）。 - 有料枠: 月額最低 $5 から（要再確認）。詳細は Cloudflare Workers Pricing を参照。 - 留意事項: 記載の金額は為替レートおよび税金を除外した概算である。対象アカウントにおける現行プランの契約状況は未確認であり、無料枠の永続的な適用を保証するものではない。全文検索インデックス作成を伴う全量データ取り込み処理では書き込み行数が多くなるため、1 日あたりの無料枠（10 万行）を超過する可能性がある。
